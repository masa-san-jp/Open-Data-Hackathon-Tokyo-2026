# AGENTS.md ─ はしごゆ

このリポジトリで作業するエージェントへの指示。**着手前に必ず全文を読む。**

---

## 0. 読む順序

1. この文書
2. `../../docs/design/hashigoyu/spec.md` ─ 唯一の仕様。ここに無い機能を作らない
3. `../../docs/design/hashigoyu/plan.md` ─ フェーズとタスク定義

---

## 1. 実行ループ

```
1. `../../docs/design/hashigoyu/plan.md` から、状態が「未着手」かつ依存がすべて「完了」のタスクを1つ選ぶ
2. そのタスクの「作るもの」「内容」「受け入れ条件」を読む
3. 未決事項（spec §9）に触れるか確認する。触れるなら §4 に従って保留する
4. 実装する
5. そのタスクの「検証」コマンドを実行する
6. 失敗したら 4 に戻る。3回失敗したら §5 に従って報告し、次のタスクに移らない
7. 成功したら `../../docs/design/hashigoyu/plan.md` の状態を「完了」に更新し、変更をコミットする
8. 1 に戻る
```

**複数タスクを並行して進めない。1タスクずつ、検証が通るまで次に行かない。**

## 2. 守ること

### 2-1. 仕様の逸脱を作らない

- `../../docs/design/hashigoyu/spec.md` §3 の型を追加・改名・削除しない
- §4 の計算式を変えない。数値が合わないときは、式ではなくテストの期待値を確認する
- §8 の配色・書体を変えない
- 仕様に無い画面・機能・設定項目を追加しない

### 2-2. 使わないもの

- **`localStorage` / `sessionStorage`**（動作環境で使用不可）
- CSS フレームワーク（Tailwind、Bootstrap 等）
- 状態管理ライブラリ（Redux、Zustand 等）。React state と `packages/store` で足りる
- ORM。SQL を直接書く
- `any`。`unknown` で受けて絞り込む

### 2-3. データの真正性

- **架空のデータを実データとして表示しない**
- 出典が確認できない数値を画面に出さない
- 3アプリすべてに「銭湯名・住所・人数・金額はすべて架空のサンプルです」を表示する（`T1-11`）
- サンプルデータを定義するファイルには、架空である旨のコメントを冒頭に書く

### 2-4. 文言

- 機能に関係のない言葉を画面に置かない
- キャッチコピー、励まし、説明的な補足、キャンペーン文言を書かない
- ラベルは名詞または短い動詞句にする

### 2-5. `demo/` を触らない

`demo/` 配下の4ファイルは Phase 0 の成果物であり、実装が壊れたときの退避先。**読むのは可。書き換え・削除は不可。**

## 3. コード規約

| | |
| :-- | :-- |
| TypeScript | `strict: true`。`any` 禁止 |
| ドメイン層 | 純関数のみ。`new Date()` `Math.random()` `fetch` を呼ばない。時刻は引数で受ける |
| 副作用 | `apps/` と `packages/store` に閉じる |
| 日本語 | UI 文言は `*.ja.ts` に分離し、計算ロジックと混ぜない |
| 命名 | ドメイン用語は `spec.md` の表記に合わせる（`requiredDailyVisitors` を `target` と略さない） |
| コミット | `[T1-03] 計算関数を実装` の形式。タスクIDを必ず含める |

## 4. 未決事項に触れたとき

`../../docs/design/hashigoyu/spec.md` §9 の `U1`〜`U7` に該当する判断が必要になったら、**推測で決めずに停止する。**

```
1. そのタスクの状態を `../../docs/design/hashigoyu/plan.md` で「保留（U○ 待ち）」に更新する
2. 何を判断してほしいかを1行で書く
3. 選択肢と、それぞれを選んだ場合に何が変わるかを書く
4. 次のタスクに移る（依存関係で進めるものがあれば）
```

**「とりあえずこうしておく」を選ばない。** 特に以下は必ず停止する。

- 運営主体・権限設計に関わる決定（`U1`）
- 実データの取得元（`U2` `U3` `U4`）
- 提案スコアの重み変更（`U6`）

---

## 5. 詰まったときの報告形式

3回失敗したら、次を書いて停止する。

```
タスク: T1-0X
やろうとしたこと:
エラー:
試したこと（3つ）:
仕様のどこが不明確か:
```

**仕様が不明確なまま実装を続けない。**

---

## 6. 検証コマンド

タスク完了前に、そのタスクの検証コマンドに加えて次を通す。

```bash
pnpm -r exec tsc --noEmit     # 型エラー 0
pnpm -r test                  # 全緑
```

Phase 完了時はさらに次も通す。

```bash
pnpm -r build
pnpm e2e
```

**テストを消して緑にしない。テストを緩めて緑にしない。** 期待値が間違っていると判断した場合は、`spec.md` の該当箇所を引用して根拠を示してから変更する。

---

## 7. タスクの完了定義

すべて満たしたときのみ「完了」にする。

- [ ] `docs/plan.md` に書かれた受け入れ条件をすべて満たしている
- [ ] そのタスクの検証コマンドが通る
- [ ] `pnpm -r exec tsc --noEmit` が通る
- [ ] `pnpm -r test` が通る
- [ ] `spec.md` に無い機能を追加していない
- [ ] `demo/` を変更していない
- [ ] タスクIDを含むコミットメッセージでコミットした

---

## 8. 優先順位

判断に迷ったら、この順で決める。

1. **仕様どおりであること**（`spec.md`）
2. **検証が通ること**
3. 既存のデモと見た目が一致すること
4. コードの短さ

3 と 4 のために 1 と 2 を崩さない。
