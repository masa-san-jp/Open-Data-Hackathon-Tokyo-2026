# AIエージェントを用いた行政サービスデザインと行政経営の世界事例調査

> 原文: [Google Docs](https://docs.google.com/document/d/1lLqofHmDR0vImn6YrpweXLXuR8OWN4Foe1AE8QcxbCc)

## エグゼクティブサマリー

本報告書は、2026年8月6日時点で公開情報を確認できる行政AIエージェントの主要事例を、国・自治体・行政機関、先進国・新興国、住民向けサービス・職員向け行政経営、実世界・仮想世界を横断して比較したものである。対象には、日本のガバメントAI「源内」、エストニアのBürokratt、シンガポールのVICA、英国のGOV.UK Chat、ウクライナのDiia.AI、インドのKisan e-Mitra、ブエノスアイレスのBoti、ボゴタのChatico、ニューヨーク市のMyCity、ドバイのDubai.AIおよびDEWAのRammas、フィンランドのAuroraAI、韓国のMetaverse Seoulなどを含めた。

最も重要な結論は、**行政分野で実績を上げているAIエージェントは、完全自律型ではなく、対象業務、参照情報、実行可能な操作、権限を限定した「制約されたエージェント」である**という点である。シンガポールのVICAは決定論的なFAQ・自然言語処理と生成AIを組み合わせ、行政機関が生成結果を上書きできる構造を採用している。英国のGOV.UK Chatは、政府公式コンテンツに限定した検索拡張生成、専門職員による評価、レッドチーム、継続監視を組み合わせた。エストニアのBürokrattも、各機関のAIエージェントを連携させる将来像を掲げつつ、現在は各機関の公式情報に基づく回答と人間への引継ぎを中心としている。

行政AIエージェントの発展段階は、概ね「FAQ・検索」「公式情報に基づくRAG」「本人認証を伴う個別情報照会」「申請・証明書発行等の取引実行」「複数機関・複数エージェントによるサービス編成」の順に整理できる。2025年に公開されたウクライナのDiia.AIは、本人認証、行政レジストリ照会、証明書発行を対話画面内で実行し、外部大規模言語モデルに個人情報を渡す前に仮名化・マスキングする構成を公開している。これは、単なる行政チャットボットから、権限管理された「行政トランザクション・エージェント」への移行を示す先進例である。

一方、導入規模や会話数だけでは成果を判断できない。GOV.UK Chatは二つのパイロットで1万人超、約2万6,000件の質問を処理し、回答精度を76%から90%へ改善したが、有用性評価は73%、満足度は64%であり、一定の不満が残った。ニューヨーク市MyCityでは、2025年7〜8月に回答評価を行った70人のうち約71%が否定的評価を付け、市監査院が不正確・不整合な回答と応答遅延を指摘した。行政AIでは利用量よりも、正答率、手続完了率、誤案内率、権利侵害の有無、人間への適切な引継ぎ、再問い合わせ率を重視する必要がある。

規模拡大に成功している事例には、個別機関が一からシステムを構築するのではなく、**政府共通基盤を用いる**という共通点がある。VICAは60超の行政機関、100超のチャットボットで月平均80万件超の問い合わせを処理する。Bürokrattは国・地方政府が利用できる共通ソフトウェアと国家クラウドを提供し、ソフトウェア自体は無料、標準的なホスティング費用は月約150ユーロと公表している。ただし、この金額にはコンテンツ整備、連携開発、LLM利用料、評価・監査、運用要員は含まれない。日本の「源内」も、政府共通基盤、共通データセット、行政特化アプリ、複数モデルの共用へと進んでいる。

仮想世界については、**メタバースは行政AIエージェントそのものではなく、チャネルまたはユーザーインターフェースである**と捉えるべきである。Metaverse Seoulは、仮想市庁舎、相談、証明書、税務相談、首長室への意見提出を提供したが、中心はアバターを介した人間同士の対話や既存サービスへの接続であり、高度なAIエージェントではなかった。2023年1月の正式公開後、2024年10月16日にサービスを終了している。これに対し、DEWAは仮想空間DEWAverseを運営しつつ、顧客対応AIのRammas、内部開発・テスト用AIエージェントを既存デジタルチャネルにも展開している。仮想空間を独立した目的にせず、既存の行政サービス基盤とAIエージェントの追加チャネルとして扱う方が実務的である。

小規模自治体では、最初から申請実行型やメタバース型を目指すべきではない。推奨される導入順序は、①対象サービスを一つに限定、②個人情報を扱わない公式情報RAG、③限定公開と人間への引継ぎ、④評価用質問セットと誤案内監視、⑤本人認証後の照会機能、⑥一つの基幹システムとの取引連携、である。標準的な初期実証は300万〜800万円、本人認証・基幹連携を含む取引型は1,500万〜4,000万円程度を目安とし、単独調達より国・都道府県・複数自治体による共通基盤を優先すべきである。

## 調査範囲と比較フレーム

本報告書における「AIエージェント」は、自然言語や音声による要求を理解し、情報検索、サービス選択、分類、行政組織への振分け、個別データ照会、申請・予約・証明書発行、内部行政プロセスの一部を実行するシステムを指す。固定シナリオ型チャットボットも比較対象に含めるが、単なるウェブ検索やRPAだけの事例は原則として除外した。

比較のため、各事例の成熟度を次のように整理した。これは本報告書独自の分析区分であり、各政府が公式に採用している分類ではない。

| 成熟度 | 定義 | 代表的な能力 |
| :-- | :-- | :-- |
| **A0：仮想チャネル型** | 3D空間やアバターを提供するが、AIによる自律的な判断・実行は限定的 | 仮想窓口、アバター相談、イベント、既存サービスへのリンク |
| **A1：応答・分類型** | FAQ、決定木、自然言語分類を用いる | FAQ回答、問い合わせ分類、担当機関振分け |
| **A2：根拠付き生成型** | 政府公式情報をRAG等で検索し、生成AIが回答する | 文脈理解、要約、引用・参照、複数言語 |
| **A3：取引実行型** | 本人認証後に行政システムを呼び出し、照会・申請等を実行する | 個別情報照会、予約、証明書発行、申請補助 |
| **A4：連携・マルチエージェント型** | 複数機関・複数システムのエージェントを編成し、生活イベント単位で処理する | 部門横断サービス、プロアクティブ通知、複数手続の連続実行 |

主な調査対象は直近10年間とし、AuroraAIのように、現在の行政AIエージェント政策へ重要な教訓を与えた構想・終了事例も含めた。公開資料の信頼度は、政府・自治体公式情報、政府監査、国際機関、原著・査読研究、政府と技術事業者の共同技術解説の順に重視した。ベンダー共同資料に記載された性能値は、独立監査済みでない場合、その旨を明記する。

## 技術アーキテクチャの共通パターンと差異

行政AIエージェントの標準的な構成は、利用チャネル、認証・同意、エージェント・オーケストレーター、ポリシー・ガードレール、公式情報検索、行政システム接続、人間への引継ぎ、監査・評価の八層に整理できる。

> 原文にはこの八層を示すフロー図が含まれていた（Google Docs のエクスポートでノードのみが残ったため、以下の構造で置き換える）。

1. **利用者** — 住民・事業者・職員
2. **利用チャネル** — Web・行政アプリ／WhatsApp・SNS／音声・電話／3D空間・アバター
   - APIゲートウェイを経由
   - 3D空間・アバターの場合は、空間セッション・アバター安全管理を追加
3. **分岐：本人認証が必要か**
   - 必要 → eID・同意・権限・セッション管理
   - 不要 → そのままオーケストレーターへ
4. **エージェント・オーケストレーター**
5. **ポリシーエンジン・ガードレール**
6. **処理の実行系**
   - 公式情報RAG・検索 → 法令・FAQ・手続・行政文書
   - LLM・NLU・モデルルーター
   - ツール実行・MCP・行政API → 申請・予約・CRM・ケース管理／行政レジストリ・給付・決済／他機関・他エージェント
7. **人間オペレーターへの引継ぎ**
8. **監査ログ・評価・コスト監視** → 品質管理・モデル更新・停止判断

この構成は、GOV.UK Chatの公式コンテンツRAG、Diia.AIのMCPとTrembitaによる行政レジストリ接続、VICAの機関別ナレッジと生成出力の上書き、Bürokrattの機関別エージェント・グローバル分類器、DEWAのAgent Development Kitなどから抽出できる。

| アーキテクチャ・パターン | 適する業務 | 代表事例 | 長所 | 主なリスク |
| :-- | :-- | :-- | :-- | :-- |
| **決定木＋NLU分類** | 定型FAQ、案件分類、担当振分け | OneService初期、Boti初期、Kisan e-Mitraの一部 | 再現性が高い、挙動を管理しやすい | 表現揺れ、未知質問、維持管理負担 |

| **連携・マルチエージェント** | 生活イベント、部門横断処理 | Bürokratt将来像、AuroraAI構想、UAE構想 | 利用者が機関構造を意識せずに済む | エージェント間の責任、連鎖誤作動、権限伝播 |
| **没入型・空間チャネル** | 都市計画、訓練、観光、遠隔相談、共同設計 | Metaverse Seoul、DEWAverse | 空間理解、参加感、遠隔共同作業 | 高コスト、端末格差、低利用率、アバター詐称、行動追跡 |

技術面で最も重要なのは、LLMの選定よりも、①信頼できる知識を誰が更新するか、②どの行政APIをどの権限で呼び出せるか、③誤回答・誤実行をどの段階で止めるか、④人間へどの条件で引き継ぐか、⑤モデル変更後も評価結果を再現できるか、である。

行政AIで推奨されるデータフローは、Diia.AIのように、実データを行政側の信頼境界内に保持し、外部モデルには仮名化されたスロットや必要最小限の情報のみを送る方式である。モデルの出力を受け取った後、行政側で実データへ再置換する。この方式は万能ではなく、会話内容自体から本人の属性が推定される可能性があるため、自由記述のフィルタリング、再識別リスク評価、プロンプト・ログへのアクセス統制も必要である。

## ガバナンス・リスク管理と仮想世界設計

### ガバナンスのベストプラクティス

NIST AI Risk Management Framework、OECD AI原則と政府AI関連報告、UNESCOのAI倫理勧告、カナダ政府のAlgorithmic Impact Assessment、EU AI法、日本政府のAI調達・利活用ガイドラインは、リスクに応じた評価、透明性、人間による監督、データガバナンス、継続監視を共通して重視している。行政AIでは、一般企業の顧客対応以上に、法令上の権利、給付、許認可、期限、平等取扱い、説明責任を保護する必要がある。

| リスク領域 | 必須統制 | 運用上の証拠 |
| :-- | :-- | :-- |
| **責任の所在** | サービス責任者、データ責任者、モデルリスク責任者、セキュリティ責任者を分離して指名 | RACI、承認記録、緊急停止権限、インシデント報告先 |
| **利用目的・権限** | 「案内」「推薦」「下書き」「照会」「実行」「決定」を明確に区別 | 機能別の許可表、実行可能ツール一覧、禁止操作一覧 |
| **権利に関わる判断** | 給付不支給、許認可拒否、制裁、採用、福祉優先度等をLLM単独で決定させない | 人間の最終決定、理由記録、異議申立て・再審査経路 |
| **データ保護** | 目的限定、最小化、仮名化、保存期間、外部モデル学習禁止、越境移転確認 | データフロー図、DPIA、処理記録、削除試験、契約条項 |
| **回答の根拠** | 公式情報に限定したRAG、参照元、施行日・更新日表示 | ソースURL履歴、検索結果、文書版、回答生成時の参照記録 |
| **エージェントの実行権限** | 最小権限、短時間トークン、取引前確認、金額・件数上限、再実行防止 | IAM設定、ツール呼出ログ、利用者確認画面、取消ログ |
| **品質評価** | 代表質問、少数言語・方言、曖昧質問、敵対入力を含む固定評価セット | 正答率、根拠一致率、拒否精度、言語別指標、回帰試験 |
| **セキュリティ** | プロンプトインジェクション、データ抽出、権限昇格、ツール悪用の試験 | レッドチーム報告、脆弱性修正、侵入検知、鍵ローテーション |
| **人的統制** | 人間への引継ぎ、オペレーター用の会話要約、AI回答訂正権限 | 引継ぎ率、待ち時間、再問い合わせ率、訂正履歴 |
| **透明性** | AI利用の明示、能力・限界、データ利用、異議申立て、連絡先を表示 | 公開AI台帳、モデル・システムカード、変更履歴 |
| **調達・ベンダー管理** | データ移行、モデル切替、ログ持出し、終了支援、価格改定上限を契約化 | 出口計画、オープンAPI、データ形式、代替モデル試験 |
| **継続監視・停止** | モデル更新後の再評価、誤案内急増時の自動縮退、旧方式への切戻し | ダッシュボード、閾値、停止手順、障害訓練、月次レビュー |

会話件数や削減時間だけをKPIにすると、AIが回答を増やしたものの、利用者が解決できず再問い合わせしている状況を見逃す。最低限、次の式で行政サービスとしての実効性を測る必要がある。

> **有効完了率 ＝ 正しい案内または取引完了件数 ÷ 全利用セッション数**

これに、誤案内率、根拠不一致率、期限・金額の誤り、取引取消率、人間への適切な引継ぎ率、言語別格差、アクセシビリティ達成率、1有効完了当たり総コストを併記する。GOV.UK Chatのように、自動評価、専門家評価、レッドチーム、実利用評価を重ねる方式が望ましい。

### 仮想世界特有の設計上の留意点

| 論点 | 仮想世界特有のリスク | 設計・政策上の対応 |
| :-- | :-- | :-- |
| **本人性とアバター** | 公務員・住民のなりすまし、代理人資格の不明確化 | 公的eIDと表示名を分離し、認証済み公務員バッジ、代理権確認、重要操作時の再認証を導入 |
| **空間的プライバシー** | 視線、移動、近接、音声、身体動作等が通常のウェブより詳細な個人データになる | 必要最小限の行動ログ、視線・生体推定の原則禁止、録音の明示、空間別アクセス制御 |
| **会話の秘匿性** | 仮想相談室の周囲に他者が存在し、音声・字幕が漏れる | 個別相談は暗号化されたプライベート空間へ移動し、録音・スクリーンショット制御を明示 |
| **未成年者・脆弱利用者** | グルーミング、嫌がらせ、過度な没入、相談内容の漏えい | 年齢相応設計、保護者・専門職連携、モデレーション、緊急介入、滞在時間・通報機能 |
| **仮想経済** | トークン、NFT、仮想財の投機、行政優遇との混同、マネーロンダリング | 行政サービスと投機的トークンを原則分離。使用する場合は会計、返金、消費者保護、本人確認を制度化 |
| **参加型ガバナンス** | 複数アカウント、ボット投票、特定プラットフォーム利用者への偏り | 一人一票の本人確認、重複排除、対面・ウェブ・電話との並行実施、参加者属性の偏り測定 |
| **アクセシビリティ** | 高性能端末、VR酔い、視覚・聴覚・運動障害、低帯域環境 | 2Dウェブ、音声、電話、窓口を必ず併存させ、仮想空間を唯一の行政チャネルにしない |
| **記録と証拠性** | 空間内の発言・合意・操作が行政記録として残らない | 公文書管理規則に沿った会話・取引記録、タイムスタンプ、意思確認、改ざん防止 |
| **プラットフォーム依存** | 民間事業者の仕様変更、サービス終了、アバター・データ移行不能 | オープン標準、資産のエクスポート、ブラウザ対応、終了時のデータ返還、代替チャネル |
| **AIエージェントの身体性** | 人間らしいアバターが権限・能力を過大に見せる | AIであることを常時表示し、法的権限、できないこと、人間への連絡方法を明示 |

Metaverse Seoulは、仮想市長室や行政相談という新規性を示した一方、専用3Dアプリを日常の行政行為に使い続ける動機を十分に確立できなかった。専用メタバースの採否は、「空間でなければ解けない課題」があるかで判断すべきである。都市計画の3D合意形成、災害訓練、施設設計、遠隔現場支援、文化財再現などは空間性に合理性がある。一方、証明書取得、給付確認、FAQ、予約は通常のウェブ、メッセージ、音声の方が低コストでアクセシブルである。

## 導入実務チェックリストと小規模自治体パス

### 政策担当者向けチェックリスト

| フェーズ | 必須作業・成果物 | Go判断の条件 | Stopまたは再設計の条件 |
| :-- | :-- | :-- | :-- |
| **課題選定** | 問い合わせ量、処理時間、誤案内、待ち時間、既存チャネルを調査 | 高頻度で定型性があり、公式な正解情報が存在する | 問題がデータ不足や制度の複雑さにあり、AIを入れても解決しない |

| **限定公開** | 職員、協力住民、特定手続に限定し、人間窓口を併設 | 誤案内を即時修正し、フィードバックが追跡可能 | 利用者がAIを公式決定と誤認する、引継ぎ先が機能しない |
| **本番運用** | 日次監視、月次品質会議、モデル更新審査、障害訓練 | 有効完了率、誤案内率、再問い合わせ率が改善 | 会話数のみ増え、窓口負荷・手続完了率が改善しない |
| **拡大・終了** | 新手続追加ごとに再評価、年次費用対効果、終了計画 | 共通コンポーネントを再利用できる | 高コスト・低利用でも政治的理由だけで継続する |

- データフロー図、システム構成図、API・ツール権限一覧
- AI影響評価、データ保護影響評価、脅威モデル
- 評価質問セット、正解データ、言語別・分野別評価結果
- システムカード、採用モデル一覧、モデル更新手順
- プロンプトインジェクション、情報漏えい、権限逸脱試験の結果
- 会話・ツール呼出・人間承認・モデルバージョンを結び付けた監査ログ
- 障害、誤案内、個人情報漏えい時の停止・通知・復旧手順
- 契約終了時のデータ返還・削除、代替モデル・代替事業者への移行計画

## 結論・提言

行政AIエージェントの導入目的は、「AIを導入すること」ではなく、住民が行政組織の構造や制度用語を理解しなくても、必要な情報とサービスに到達できる状態を作ることである。成功事例は、自然言語インターフェースの背後に、正確な行政コンテンツ、明確な権限、監査可能なAPI、人間の責任者、継続評価を配置している。

日本の国・自治体が採るべき第一の方針は、**共通基盤と個別サービスを分離すること**である。認証、ログ、モデルルーター、セキュリティ、評価、RAG、データマスキング、人間引継ぎは国または広域自治体で共通化し、条例、手続、施設、地域事情は各自治体が責任を持って管理する。VICA、Bürokratt、源内は、この共通基盤型の方向性を示している。

第二に、**案内と行政決定を分離する必要がある**。AIは制度説明、候補提示、書類作成支援、案件分類には積極的に利用できるが、給付拒否、許認可拒否、制裁、福祉優先度等については、法的根拠を確認できる人間が最終決定し、理由説明と不服申立てを保証すべきである。AIが行うのは決定ではなく、必要情報の整理と意思決定支援に限定するのが基本となる。

第三に、取引実行型へ進む場合は、Diia.AIが示すように、**本人認証、データマスキング、最小権限のツール接続、利用者の最終確認、暗号化、監査ログ**を一体として設計すべきである。LLMに住民データや基幹システムへの包括的アクセス権を与えてはならない。行政APIごとに、読み取り・作成・更新・取消の権限を分け、金額、回数、対象、時間帯等の制約をポリシーエンジン側で強制する。

第四に、**KPIを会話数から行政成果へ転換する必要がある**。Boti、Chatico、Kisan e-Mitraの大規模利用は包摂性と到達範囲を示す一方、会話数だけでは正しい解決に至ったか分からない。GOV.UK Chatの評価とMyCityの監査は、正答率、満足度、回答不能、応答時間、攻撃耐性を公開する重要性を示す。各自治体は、有効完了率、誤案内率、再問い合わせ率、人間引継ぎ率、言語別格差、1完了当たり費用を定例公開すべきである。

第五に、**失敗と終了を制度化するべきである**。AuroraAIは構想が大きすぎて評価可能なAIサービスへ落とし込めず、Metaverse Seoulは専用仮想空間の継続需要を確立できなかった。MyCityは運用中の不正確な回答を外部監査が明らかにした。これらは、実証に期限、予算上限、評価基準、停止条件、データ返還、利用者への終了通知をあらかじめ設定する必要性を示している。

第六に、仮想世界は、行政サービスの主要基盤ではなく、**空間的価値がある限定用途の追加チャネル**として扱うべきである。都市計画、災害訓練、施設設計、文化財、遠隔現場支援には合理性があるが、FAQ、給付照会、証明書、予約は通常のウェブ、メッセージ、音声を優先する。仮想空間を採用する場合も、公的eID、アバター認証、空間プライバシー、未成年者保護、記録管理、2D代替チャネルを必須要件とする。

最終的に目指すべき行政AIは、万能な「デジタル公務員」ではない。利用者の要求を理解し、信頼できる行政情報を検索し、必要なサービスを選び、許可された範囲で処理を実行し、判断が必要な時点で適切な職員へ引き継ぐ、**監査可能で停止可能な行政サービス・オーケストレーター**である。その実現には、高性能なモデルよりも、行政データの整備、責任分界、権限管理、評価、異議申立て、共通基盤への継続投資が決定的に重要である。
