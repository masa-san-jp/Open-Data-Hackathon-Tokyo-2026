# SILVERPUNK // 2100 先行事例・未充足領域調査

- 調査日: 2026-08-22
- 対象: [ギャップ解消詳細要件：網羅性検証レポート](https://github.com/masa-san-jp/Open-Data-Hackathon-Tokyo-2026/blob/main/docs/planning/20260822-silverpunk2100-requirements-completeness-review.md)で整理されたG1〜G16
- 目的: 各領域の国内外の先行取組を一次情報中心に一覧化し、「すでに解かれている部分」「まだ十分でない部分」「公開情報で統合先行例を確認できない部分」を切り分ける

## 1. 結論

### 1.1 「誰も取り組んでいない領域」は、領域単位では確認できない

G1〜G16のすべてで、制度、技術、サービス、標準、研究又は都市施策の先行例を確認した。したがって、**16領域のうち、構成要素に誰も取り組んでいないと判断できる領域はない**。

一方で、SILVERPUNK // 2100が必要とするのは個別要素ではなく、就労、医療、住宅、移動、文化、権利、財政を一つの都市運営として接続することである。この統合水準で見ると、次の六領域は特に未成熟である。

1. G6 高齢化の物語・社会受容
2. G7 技能・記憶の継承
3. G8 超長期資本
4. G9 都市ブランド・知財
5. G15 公平性・分配
6. G16 行政財政・調達・運用能力

これらは取組自体がないのではない。**個別のキャンペーン、保存制度、ファンド、都市ブランド、影響評価、調達標準は存在するが、当事者の権利、利益配分、長期運営、世代間公平までを一体運用する先行例を、今回調査した公開一次情報からは確認できなかった**という意味である。

### 1.2 最も先行しているのはG11・G12、最も白地が大きいのは領域間の接続部

- G11 住環境とG12 介護・福祉は、シンガポール、日本、米国等に常設・制度化された統合モデルがある。
- G1、G2、G3、G5、G10、G13、G14、G15、G16も、制度又は基盤単体では成熟している。
- しかし、**健康状態に応じて仕事を安全に再編する仕組み、技能記録のAI利用権と報酬、75年の資本・更新計画、世代・所得別の負担便益台帳**など、複数領域をつなぐ仕組みが弱い。
- SILVERPUNK // 2100の差別化余地は、新しい単体技術よりも、**既存の先行要素を権利・責任・財政・証拠で接続する都市運営モデル**にある。

## 2. 調査方法と判定基準

### 2.1 調査範囲

- 政府、自治体、国際機関、大学・公的医療機関、公式プロジェクトの公開情報を優先した。
- 商用サービスは、公式サイトで継続運用又は導入実績を確認できるものに限定した。
- 「先行例なし」は世界中に存在しないことの証明ではない。本報告では、**今回確認した公開一次情報に、同等の統合運用例が見当たらない**ことを表す。
- 研究論文を網羅するシステマティックレビューではなく、構想上の競合・参照モデルを発見するためのスコーピング調査である。

### 2.2 成熟度

| 点 | 状態 |
|---:|---|
| 4 | 法制度化、標準化又は複数地域で本番運用されている |
| 3 | 単一地域・組織で継続運用され、実利用者がいる |
| 2 | 実証、限定導入、臨床研究又は移行途上である |
| 1 | 構想、ガイドライン、単体部品又は断片的な取組にとどまる |
| 0 | 今回の公開一次情報調査では確認できない |

「要素成熟度」は領域内の最も進んだ構成要素を、「統合度」はSILVERPUNKの要件群を一体運用している程度を表す。点数は比較のための調査者判断であり、外部認証ではない。

## 6. 競争・実装上の含意

### 6.1 新規性を主張すべき場所

「高齢者住宅」「自動運転」「長寿医療」「高齢者就労」「Age-friendly city」自体を世界初とは主張できない。新規性候補は次である。

- 健康情報を最小開示の職務制約へ変換し、本人承認で仕事とアシストを同時調整すること
- 技能・記憶の収録からAI利用、継承、報酬、撤回までを権利台帳で一貫管理すること
- 住宅・ケア・仕事・移動を負担可能性とデータ同意まで含めて同一街区で運用すること
- 75年の資本・更新・撤退設計と、世代・所得別分配評価をGo/No-Go条件にすること
- 年齢にやさしい都市ブランドを、実測証拠、当事者統治、ライセンス条件に連動させること

### 6.2 直ちに実証すべき最小統合単位

最初からG1〜G16を同時実装する必要はない。白地と実現可能性の両方が高い次の三つを優先する。

1. **健康制約適応型マイクロワーク:** 職務カード、本人同意、短時間シフト、代替要員、環境改善、アシスト機器を一つの実証にする。
2. **権利付き技能継承:** 10件程度の技能を対象に、利用目的別同意、AI利用可否、教材、後継者、報酬、削除を端から端まで実装する。
3. **一つの生活OD:** 自宅から診療・仕事・買物のいずれか一目的地まで、予約、移動、翻訳、介助、通信断時代替を完遂する。

各実証は、技術稼働率だけでなく、本人便益、断念率、事故・ヒヤリハット、属性別格差、運用者工数、1件当たり総費用を測る。

### 6.3 要件文書に追加すべきフィールド

各Gの要件に、先行例と新規仮説を区別するためのメタデータを追加する。目的はURLを列挙することではなく、次の判断を監査可能にすることである。

1. 既存の制度・標準・運用・技術を、そのまま再利用できるか。
2. 東京、対象者、規模、期間、法制度等に合わせた改良が必要か。
3. どの領域間インターフェースが未検証か。
4. 何を根拠に導入し、どの条件で停止・縮小・移管するか。
5. 便益、負担、リスクが誰に偏るか。

この7フィールドは、各要件に既にある「あるべき姿・現状・ギャップ・解決方法・実行方法・完了条件」を置き換えない。また、[網羅性検証レポートの「各要件に追加すべき最小フィールド」](./20260822-silverpunk2100-requirements-completeness-review.md#12-各要件に追加すべき最小フィールド)とも併用する。

#### 6.3.1 設計原則

- **事実、推論、仮説を分離する。** 先行例が存在する事実と、東京へ移植できるという判断は別項目にする。
- **「事例がある」と「効果がある」を分離する。** 稼働の確認だけでは導入根拠にしない。対象者、期間、成果指標、限界を記録する。
- **「新規」は検索範囲付きの結論にする。** 「世界初」「誰も取り組んでいない」とは記載せず、「指定した検索範囲の公開情報では統合先行例を確認できない」と記載する。
- **未解決部分を領域名だけで表さない。** 入出力、責任主体、失敗モード、検証方法を持つインターフェースとして記述する。
- **退出条件を実証開始前に決める。** 問題発生後に都合よく閾値を変更できないよう、測定方法、判断者、停止後の処理まで定義する。
- **平均値だけで導入判断しない。** 属性別の便益、負担、リスクを確認し、不利益が集中する場合は緩和策又は補償を要件化する。
- **IDを永続化する。** 文書の章番号や行番号ではなく、改訂後も変わらないIDで要件、先行例、検索、インターフェースを接続する。

#### 6.3.2 必須フィールド仕様

| フィールド | 機械可読キー | 型 | 必須条件 | 内容・検証規則 |
|---|---|---|---|---|
| 先行例ID | `precedent_ids` | 文字列配列 | 必須 | 先行例台帳のIDを列挙する。形式は `PRE-Gxx-nnn`。該当例がない場合は空配列とし、`precedent_search_log_id`を必須にする |
| 既存で解けている部分 | `proven_components` | オブジェクト配列 | 必須 | 採用できる制度、標準、運用、技術を部品単位で記載する。各部品に先行例ID、証拠等級、適用条件、移植上の制約を付ける |
| 未解決の接続 | `unresolved_interfaces` | オブジェクト配列 | 必須 | 領域又は要件間の未検証インターフェースを記載する。接続元・先、入出力、責任、失敗モード、検証方法を必須にする |
| 模倣／改良／新規 | `novelty_class` | 列挙値 | 必須 | `REUSE`、`ADAPT`、`NEW`、`HYBRID`のいずれか。`NEW`と`HYBRID`は検索ログを必須にする |
| 導入根拠 | `adoption_evidence` | オブジェクト配列 | 必須 | 先行例の対象者、地域・規模、期間、比較対象、成果指標、結果、限界、東京への移転可能性を記載する |
| 退出条件 | `exit_conditions` | オブジェクト配列 | 実証・運用対象は必須 | 安全、権利、効果、公平性、費用、運用、法令の各観点から、トリガー、閾値、判断者、停止・縮小・移管、データ処理を定義する |
| 分配影響 | `distributional_impact` | オブジェクト配列 | 必須 | 世代、所得、障害・要介護、地域、国籍・言語等について、便益、負担、リスク、測定指標、緩和策、残余リスクを記載する |

補助キーとして、`precedent_search_log_id`、`evidence_last_verified_at`、`evidence_reviewer`を置く。空欄は認めず、該当しない場合は `NOT_APPLICABLE` と理由を記載する。未調査は `NOT_ASSESSED` とし、設計レビュー又は実証開始の判定を通過させない。

| 対象 | 形式 | 例 | 用途 |
|---|---|---|---|
| 要件 | `Gxx-n`又は`Cxx-n` | `G2-4` | 既存の要件IDを継続利用する |
| 先行例 | `PRE-Gxx-nnn` | `PRE-G02-001` | 先行例台帳の一意参照 |
| 検索ログ | `SRCH-Gxx-yyyymmdd-nnn` | `SRCH-G02-20260822-001` | 「先行例未確認」の調査範囲と再現情報 |
| 未解決接続 | `IF-Gxx-Gyy-nnn` | `IF-G02-G03-001` | 二つ以上の領域・要件間の接続仕様 |
| 退出条件 | `EXIT-Gxx-n-nnn` | `EXIT-G02-4-001` | 停止、縮小、移管、原状回復の判定条件 |
| 分配影響 | `DIST-Gxx-n-nnn` | `DIST-G02-4-001` | 属性別の便益・負担・リスク評価 |

IDは削除後も再利用しない。統合・廃止したIDは、後継IDと変更理由を履歴に残す。

#### 6.3.4 先行例台帳

各要件にURLや説明を重複記載せず、先行例を一つの台帳で管理する。各要件は`precedent_ids`で参照する。

| 台帳フィールド | 必須 | 内容 |
|---|---|---|
| `precedent_id` | 必須 | `PRE-Gxx-nnn`形式の永続ID |
| `initiative_name` | 必須 | 制度、事業、サービス、研究、標準の正式名称 |
| `jurisdiction_and_location` | 必須 | 国、自治体、地区、適用法域 |
| `operator_and_partners` | 必須 | 運営主体、責任主体、主要パートナー |
| `stage` | 必須 | `FRAMEWORK`、`PILOT`、`LIMITED_OPERATION`、`SCALED_OPERATION`、`ENDED` |
| `operational_period` | 必須 | 開始日、終了日又は継続中の別 |
| `covered_capabilities` | 必須 | 当該先行例が実際に解いている要件・機能 |
| `reported_outcomes` | 必須 | 成果指標、基準値、結果、測定期間。成果未公表の場合は明記する |
| `limitations_and_failures` | 必須 | 対象外、失敗、停止理由、サンプル限界、資金・制度制約 |
| `transfer_conditions` | 必須 | 東京へ移植する際に一致させるべき人口、法令、運用、費用等 |
| `source_urls` | 必須 | 一次情報を優先し、資料名、公開主体、公開日、URLを記載する |
| `evidence_grade` | 必須 | 下記E0〜E4 |
| `last_verified_at` | 必須 | 情報を再確認した日。`YYYY-MM-DD`形式 |
| `reviewer` | 必須 | 確認者又は確認責任チーム |

証拠等級は次のとおりとする。

| 等級 | 証拠状態 | 要件判断での扱い |
|---:|---|---|
| E4 | 法令、公的統計、監査済み実績、又は測定方法と結果を確認できる大規模本番運用 | 導入根拠として利用できる。ただし移転可能性は別途評価する |
| E3 | 公式な本番運用報告で、対象、期間、成果指標を確認できる | 条件付きの導入根拠として利用できる |
| E2 | 公式な実証評価又は査読研究で、方法と限界を確認できる | パイロット仮説の根拠として利用できる |
| E1 | 公式な制度・サービス説明又は事業者自己申告のみで、成果評価がない | 存在証明に限り、効果の根拠には使わない |
| E0 | 二次情報のみ、出典不明、古い、又は相互に矛盾する | 意思決定には使わず、追加調査対象とする |

制度や運用が存在しても成果が未公表ならE1となる。知名度、受賞歴、導入都市数だけでE3以上にしない。

#### 6.3.5 先行例検索ログ

`NEW`又は`HYBRID`を選ぶ場合は、少なくとも次を記録する。

| フィールド | 内容 |
|---|---|
| `search_log_id` | `SRCH-Gxx-yyyymmdd-nnn`形式 |
| `searched_at` | 調査日と基準時点 |
| `research_question` | 何と同等の先行例を探したか。必要機能を分解して記載する |
| `sources_searched` | 政府・自治体サイト、国際機関、論文DB、調達情報、特許等 |
| `queries_and_languages` | 使用した検索語、言語、表記ゆれ |
| `jurisdictions` | 対象国・地域。除外地域があれば理由を記載する |
| `inclusion_criteria` | 先行例と認める機能、運用期間、対象者、規模、証拠状態 |
| `exclusion_criteria` | 構想のみ、販売資料のみ、終了済みで検証不能等の除外基準 |
| `candidate_results` | 採用例、類似例、除外例とその理由 |
| `conclusion_scope` | 「どの範囲で何が確認できなかったか」。世界全体への断定は禁止する |
| `reviewer` | 調査者とレビュー者 |
| `next_review_at` | 再調査日又は再調査トリガー |

対外的な「世界初」表現は、この検索ログだけでは確定しない。特許、論文、企業事例、非公開調達を含む専門調査と法務確認を別途必要とする。

#### 6.3.6 模倣／改良／新規の判定規則

| 値 | 日本語 | 判定条件 | 実装上の扱い |
|---|---|---|---|
| `REUSE` | 模倣・再利用 | 対象者、法制度、規模、運用主体、成果条件が実質的に一致し、既存設計を変更せず採用できる | 先行例の適合確認と導入受入試験を中心にする |
| `ADAPT` | 改良・移植 | 中核機能は実証済みだが、対象者、地域、規模、法制度、運用等の変更が必要 | 変更点ごとに仮説と再検証項目を置く |
| `NEW` | 新規仮説 | 必要機能の統合先行例を指定範囲の調査で確認できず、主要部分を新たに検証する | 小規模かつ可逆な実証から開始し、証拠獲得を主目的にする |
| `HYBRID` | 複合 | 再利用可能な部品と未検証の接続を組み合わせる | 部品の再検証を最小化し、未解決接続へ評価資源を集中する |

SILVERPUNKの多くは`HYBRID`になると見込まれる。先行例が一件でもあれば`REUSE`、なければ`NEW`と機械的に判定してはならない。

#### 6.3.7 既存で解けている部分

`proven_components`は、先行例全体ではなく再利用できる部品を記述する。

| サブフィールド | 内容 |
|---|---|
| `component_id` | 要件内で一意の部品ID |
| `component` | 再利用する制度、標準、運用、技術 |
| `precedent_id` | 根拠となる先行例ID |
| `evidence_grade` | E0〜E4 |
| `proven_for` | 誰に、どの規模・期間・条件で実証されたか |
| `adopt_as_is` | 変更なしで採用できるか |
| `required_changes` | 東京又は対象要件に合わせる変更点 |
| `non_transferable_parts` | 移植できない法制度、文化、資金、組織等 |
| `verification_needed` | 採用前に再確認する事項 |

「自動運転は実用化済み」のような広い記述は禁止する。「限定ODDにおける遠隔監視型レベル4運行」のように、実証された境界を維持する。

#### 6.3.8 未解決の接続

白地は、多くの場合、領域内の機能ではなく領域間の接続にある。`unresolved_interfaces`は次の単位で記述する。

| サブフィールド | 内容 |
|---|---|
| `interface_id` | `IF-Gxx-Gyy-nnn`形式 |
| `from_requirement_id` | 接続元の要件ID |
| `to_requirement_id` | 接続先の要件ID。三つ以上の場合は配列にする |
| `purpose` | この接続で実現する本人・運用上の価値 |
| `input` | データ、物、意思決定、サービス要求等の入力 |
| `output` | 相手側へ渡す出力と品質・時間条件 |
| `rights_and_consent` | 同意、拒否、撤回、代理権、最小開示、保存期間 |
| `responsible_owner` | 接続を端から端まで成立させる責任者 |
| `failure_modes` | 遅延、誤り、停止、誤解、責任空白等 |
| `safe_fallback` | 失敗時の安全側縮退、人手代替、オフライン手段 |
| `validation_method` | 正常系、異常系、撤回、災害時を含む検証方法 |
| `acceptance_threshold` | 完了とみなす品質、時間、事故、断念率等の閾値 |

接続元と接続先が決まっていても、端から端までの責任者がいなければ未解決と判定する。

#### 6.3.9 導入根拠

`adoption_evidence`は、先行例の紹介文ではなく、導入判断に使う証拠を構造化する。

| サブフィールド | 内容 |
|---|---|
| `precedent_id` | 証拠の出所となる先行例 |
| `population` | 年齢、健康状態、障害、所得、利用条件等 |
| `jurisdiction_and_scale` | 法域、施設数、利用者数、地区規模等 |
| `observation_period` | 評価期間と追跡期間 |
| `comparison` | 導入前、対照群、代替手段等。ない場合は明記する |
| `metric` | 成果、過程、安全、費用、公平性の指標 |
| `baseline` | 導入前又は比較対象の値 |
| `reported_result` | 先行例で報告された結果 |
| `failure_condition` | 先行例で未達、事故、停止となった条件 |
| `limitations` | サンプル、測定、選択バイアス、外的妥当性等 |
| `transferability_assessment` | 東京で同等効果を期待できる条件と不確実性 |
| `local_validation_needed` | 東京で改めて測る指標と理由 |

一つの先行例だけで導入を決めず、安全、効果、費用、運用、公平性を異なる証拠で補完する。E1以下しかない場合は「導入」ではなく「仮説検証」として扱う。

#### 6.3.10 退出条件

`exit_conditions`は「問題があれば中止する」では不十分である。少なくとも次の七分類を検討する。

| 分類 | 主な監視対象 | 退出時の例 |
|---|---|---|
| 安全 | 重大事故、ヒヤリハット、誤作動、医療悪化 | 即時停止、安全確認、代替サービスへ切替 |
| 権利・プライバシー | 無断利用、撤回未反映、目的外利用、苦情未処理 | データ処理停止、削除・訂正、第三者監査 |
| 効果 | 本人便益、断念率、健康・生活成果が最低基準未満 | 改良、対象縮小、又は終了 |
| 公平性 | 特定属性の利用率・不利益・事故率が悪化 | 新規受付停止、是正、補償、再設計 |
| 経済性 | 1件当たり総費用、費用超過、継続資金不足 | 規模縮小、料金・資金構成見直し、事業移管 |
| 運用能力 | 人員、保守、稼働率、応答時間、供給者撤退 | 手動運用、代替供給者、段階停止 |
| 法令・社会受容 | 法令変更、許認可失効、重大な反対・信頼低下 | 該当機能停止、再同意、再承認 |

各退出条件は次を必須とする。

```text
exit_condition_id
category
trigger_metric
measurement_method
threshold
monitoring_frequency
decision_owner
approver
immediate_action
rollback_or_migration_plan
service_continuity_plan
data_disposition
participant_communication
restart_conditions
```

閾値は実証開始前に設定し、未確定の`TBD`がある要件はGo判定を通さない。重大事故等の即時停止条件と、複数回の未達で改良判断する条件を分ける。

#### 6.3.11 分配影響

`distributional_impact`は、全体平均では隠れる便益・負担・リスクの偏りを記録する。最低限、次の軸を確認する。

- 年齢・世代: 現在の高齢者、将来世代、若年・現役世代
- 所得・資産: 所得階層、住宅所有、費用負担能力
- 障害・健康・介護: 身体、感覚、認知、精神、慢性疾患、要介護度
- 地域: 都心・周辺・島しょ、対象地区内外、移動距離
- 国籍・在留・言語: 日本語能力、在留資格、制度アクセス
- 性別・家族・ケア責任: 単身、家族介護者、ひとり親等
- デジタルアクセス: 端末、通信、認証、支援者、デジタル技能

該当しない軸は削除せず、理由を記載する。評価表は次の形式とする。

| `dimension` | `group` | `benefit` | `burden` | `risk` | `metric` | `baseline` | `expected_change` | `mitigation_or_compensation` | `residual_risk` | `owner` |
|---|---|---|---|---|---|---|---|---|---|---|
| 年齢・世代 | 例: 現在の高齢者 | 何が改善するか | 金銭・時間・同意負担 | 安全・排除等 | 測定指標 | 現状値 | 改善・悪化方向 | 緩和・補償 | 残る不利益 | 責任者 |

分配影響は説明資料にとどめず、料金減免、代替導線、住宅確保、追加支援、利益還元等の要件へ接続する。重大な不利益が緩和できない場合はNo-Go条件とする。

#### 6.3.15 既存の管理フィールドとの対応
