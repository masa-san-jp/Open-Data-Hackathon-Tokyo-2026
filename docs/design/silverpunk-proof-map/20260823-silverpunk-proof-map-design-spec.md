# SILVERPUNK PROOF MAP — 設計仕様書

作成日: 2026-08-23  
状態: 実装着手可能な初版  
対象: 都知事杯オープンデータ・ハッカソン2026  
実装先: `apps/silverpunk-proof-map/`

## 1. 目的

### 1.1 解く課題

「2100年の東京」という長期の人口・気候変化を、住民と行政が今日の生活圏の判断に使える情報へ翻訳する。

高齢者・要配慮者が、猛暑や災害時に次の場所へ無理なく到達できるかを、地区単位で確かめる。

- 涼しく休める場所
- 給水・トイレ・休憩拠点
- 医療・介護・福祉の相談先
- 避難所・避難場所
- 公共交通・バリアフリー情報
- これらを横断して比較するために不足しているデータ

### 1.2 プロダクト仮説

人口の高齢化、昼間の支え手、暑熱・災害、生活支援拠点、データ欠損を一つの地区カードに束ねると、「何となく危ない地区」ではなく「次に何を検証すべき地区か」を説明できる。

これは経路の安全を保証するナビゲーションではない。公開データで確認できた事実と、確認できない事実を分け、パイロットの優先順位をつける意思決定支援である。

### 1.3 デモの一文

> 猛暑と人口構造の変化を重ね、支援が必要な人に生活拠点が届くかを地区ごとに見える化し、最初の30日で確かめる行動まで出す。

## 2. 利用者と利用場面

| 利用者 | 困りごと | デモで得るもの |
| :-- | :-- | :-- |
| 都民・家族・支援者 | 暑い日や災害時に、どこへ行けばよいか分からない | 生活圏の拠点、注意点、未確認情報 |
| 区市町村の担当者 | 地区ごとの優先課題を説明しにくい | 根拠つき地区比較とデータ整備候補 |
| 地域の実証運営者 | どこから試すか、何を測るかが曖昧 | パイロットカードと30日アクション |
| 審査員・協力者 | 構想がデータ活用になっているか知りたい | 出典、計算式、欠損、再現手順 |

個人の健康情報、要介護認定、位置履歴、適性、収入などは扱わない。画面は匿名・集計済みの公開情報だけで成立する。

## 3. デモの成功条件

初見の人が60秒以内に、次の4点を理解できること。

1. なぜこの地区を見ているのか（猛暑・高齢者・災害・生活拠点の関係）
2. どの地区が相対的に優先候補なのか
3. その判断に使ったデータと、まだ分からないことは何か
4. 次の30日間に何を現地で確かめるのか

### 3.1 Phase 1 の画面受け入れ条件

- `prototype/index.html` をビルドなしで開ける
- シナリオを1つ以上選べる
- 地区候補を3件以上一覧でき、並べ替えができる
- 地区詳細に指標、出典、取得日、計算できない項目が出る
- 「データがない」を推定値で埋めず、`未確認` と表示する
- 1地区のパイロットカードに、仮説・30日アクション・中止条件が出る
- 画面下部に免責とデータ利用上の注意がある
- オフラインで動作する（ブラウザから外部 URL を呼ばない）

## 4. フェーズ境界

| フェーズ | 成果 | 実装範囲 | 完了の意味 |
| :-- | :-- | :-- | :-- |
| **Phase 0: Contract** | 実装の骨格 | ディレクトリ、JSON 契約、検証コマンド、空画面 | エージェントが迷わず T01 に着手できる |
| **Phase 1: Demo** | すぐ動く静的プロトタイプ | シナリオ、ランキング、詳細、根拠、欠損、アクションカード | 60秒デモをオフラインで再生できる |
| **Phase 2: Evidence** | 検証済みデータの更新 | 都の公開データ取得、正規化、出典マニフェスト、再計算 | データ更新後も同じ画面を再生成できる |
| **Phase 3: Decision** | 地区選定ツール | T4 スコアリング、T7 暑熱×要支援、T8 欠損、T9 カード | 上位候補と次の30日の実証計画を比較できる |
| **Phase 4: Spatial** | 空間的な検証 | GeoJSON/SVG 地図、避難・拠点の位置、ルート候補 | 地図上で根拠を追える。経路の安全保証ではない |
| **Future** | 運用 | データ更新自動化、住民フィードバック、API、個別最適化 | 今回の提出スコープ外 |

Phase 1 は Phase 2〜4 の入力が一部未検証でも成立するように作る。将来機能のために最初のデモを遅らせない。

## 5. 機能要件

### FR-01 シナリオ選択

画面上部にシナリオを置く。初版は `heat_disaster`（猛暑・災害）を必須とし、`population_2100`（2100年視界切れ）を任意で持つ。

シナリオは表示文言、使用指標、注意書き、データ状態を JSON から読み込む。コード中にシナリオ固有の数値や説明を散在させない。

### FR-02 東京全体の見出し

既存の実測データを再利用できる場合は、東京全体の次のような変化を最上部に表示する。

- 65歳以上の昼間就業者
- 全就業者
- 65歳以上人口と支え手比率

出典が異なる年次・粒度を混ぜる場合は、同じ指標として表示しない。算出不能なら数値ではなく `算出対象外` を表示する。

### FR-03 地区候補一覧

各行・カードには次を表示する。

- 地区名（区市町村、またはデータが揃ったモデル地区）
- 対象人口・65歳以上人口・高齢化率
- 昼間就業者・65歳以上就業者・支え手比率（存在する場合）
- 暑熱・災害の対象拠点数（検証済みの場合）
- 生活支援拠点数（医療、介護、休憩等。カテゴリ別）
- データ欠損数または `横並び比較不可`
- 優先順位と、そのスコアの版

既定の並び順はシナリオの優先スコア降順。指標列を押して並べ替えられる。順位の意味を「危険度」や「安全保証」と表現しない。

### FR-04 地区詳細

地区を選ぶと、次の順で表示する。

1. その地区を候補にした一文
2. 指標カード（値、単位、対象年、データ状態）
3. 確認済みの拠点一覧またはカテゴリ別件数
4. 計算式と比較対象
5. 未確認・欠損・対象外の項目
6. 出典と取得日
7. パイロットカードへの導線

### FR-05 根拠・再現性

すべての表示値は、最低限 `claim_id`、`source_id`、`as_of`、`status`、`calculation` をたどれること。画面では簡潔に、JSON とマニフェストでは完全に記録する。

### FR-06 欠損の表示

データがない場合は、次のどれかを明示する。

- `missing`: 公開データで見つからない
- `not_comparable`: 地区間で粒度・定義が揃わない
- `not_verified`: URL はあるが中身未確認
- `not_applicable`: シナリオ対象外
- `stale`: 取得日が基準日を超えて古い

「0件」と「未確認」を同じ見た目にしない。欠損はプロダクトの主張であり、隠さない。

### FR-07 パイロットカード

選択地区ごとに、次の固定構造を表示する。

- 仮説: 何が不足している可能性があるか
- 30日アクション: 現地確認、データ照合、協力先確認など最大3件
- 測定指標: 到達できた拠点数、未確認地点数、休憩間隔など。未取得なら `測定方法を決める` とする
- 中止条件: 危険情報が確認できない、協力先不在、同意が得られない等
- 次の判断: 継続、条件変更、別地区へ切り替え

個人の医療判断、避難命令、移動の安全保証は出さない。

### FR-08 地図（Phase 4）

Phase 1 の必須要件ではない。導入時はランキングとカードだけで成立させる。Phase 4 で位置データと境界が揃ったら、SVG またはローカル GeoJSON を使って次を表示する。

- 地区境界
- 避難所・休憩・給水・医療・介護拠点
- データ状態（確認済み／未確認）

外部タイル、経路 API、CDN を必須にしない。地図が読み込めなくても、一覧・根拠・カードは使えること。

### 6.3 指標と計算規則

| 指標 | 定義 | 条件 |
| :-- | :-- | :-- |
| `aged_share` | `65歳以上人口 / 総人口` | 分母・対象年・地域粒度が一致すること |
| `supporter_ratio` | `昼間就業者 / 65歳以上人口` | 年次と自治体名が一致すること |
| `facility_count` | 指定カテゴリの確認済み施設数 | 同じカテゴリ定義と対象範囲を使うこと |
| `heat_disaster_need_score` | 入力を正規化した比較用スコア | 全必須入力が `verified` のときだけ算出 |
| `data_gap_count` | `missing` または `not_comparable` の項目数 | 「0施設」とは別フィールドにする |

`heat_disaster_need_score` の初版式は、実データの定義を確定してから固定する。仮に採用する場合は次のように版管理する。

```text
score_v1 = 0.45 × norm(aged_share)
         + 0.35 × norm(hazard_exposure)
         + 0.20 × norm(1 / max(support_points, 1))
```

ただし、`hazard_exposure` や `support_points` が未検証ならスコアを出さず、`not_computable` と表示する。Phase 1 の順位は、実際に利用した入力だけを明記した「demo priority」とし、災害リスクや安全性の順位と呼ばない。

### 6.4 出典と主張の台帳

主張は UI の文章ではなく `claims.json` を原本にする。

```json
{
  "id": "claim-heat-shelter-coverage",
  "text": "この地区のクーリングシェルター公開情報は横並び比較に未対応",
  "status": "verified",
  "sources": ["catalog-20260704"],
  "calculation": "カタログ検索結果を地区単位で確認。網羅性は保証しない",
  "limitations": "公開カタログにない施設の不存在を意味しない"
}
```

`verified` は「ソースを開き、粒度・定義・取得日を確認した」意味に限定する。URL を見ただけのものは `not_verified` とする。

## 7. 画面仕様

### 7.1 画面構成

```text
┌──────────────────────────────────────────────┐
│ SILVERPUNK PROOF MAP                         │
│ 猛暑・災害シナリオ [切替]  データ基準日       │
├──────────────────────────────────────────────┤
│ 2100年の未来を、今日の生活圏で確かめる        │
│ [対象地区数] [高齢者指標] [未確認項目]         │
├──────────────────────────────────────────────┤
│ 地区候補       優先度  高齢化  拠点  欠損       │
│ ──────────────────────────────────────────── │
│ A地区          ---     ...     ...   ...       │
│ B地区          ---     ...     ...   ...       │
├──────────────────────────────────────────────┤
│ 選択地区: A地区                               │
│ 根拠 / 拠点 / 未確認 / 30日パイロットカード    │
├──────────────────────────────────────────────┤
│ 出典・計算式・限界 / 緊急時は公式情報を確認     │
└──────────────────────────────────────────────┘
```

### 7.2 表現のルール

- スコアは「優先候補」「比較用」と表示し、「危険度」「安全度」と断定しない
- `0`、`未確認`、`比較不可`、`算出対象外` を別表示にする
- 各数値の横に対象年とデータ状態を置く
- 色だけで意味を伝えず、ラベルとアイコン形状・テキストを併用する
- 高齢者を一括して脆弱な存在と表現せず、地域の担い手・利用者としても描く
- 災害時の行動は、自治体・気象庁等の公式情報を優先する旨を明記する

### 7.3 Phase 1 の操作

- シナリオボタンを押す
- 列見出しを押して並べ替える
- 地区カードを押して詳細を開く
- 「根拠を見る」を押して出典・式・取得日を開く
- 「30日カード」を押して実証計画を表示する

## 8. 技術仕様

### 8.1 Phase 1 の最小構成

- HTML + CSS + Vanilla JavaScript
- Python 標準ライブラリだけのデータ生成・検証スクリプト
- `prototype/index.html` は生成可能な単体ファイル
- データは HTML に埋め込む。`file://` で `fetch()` しない
- 外部 CDN、外部タイル、ログイン、API キー、バックエンドを必須にしない

### 8.2 Phase 2 以降

- 取得は `scripts/fetch_sources.py` に閉じ込める
- 生データを `data/raw/`、正規化データを `data/normalized/` に分ける
- 区市町村コードを第一キーとし、名称は表示用にする。コードがない場合は表記ゆれ表を保存する
- `build_dataset.py` は決定的に同じ JSON を生成する
- `verify.py` は件数、型、必須項目、固定点、出典状態、欠損の表示を検査する
- ブラウザの表示は生成済み静的 JSON/HTML に依存し、実行時のデータ取得を避ける

### 8.3 セキュリティ・プライバシー

- 個人を識別できる情報、健康情報、位置履歴を保存・表示しない
- API キーや認証情報をコミットしない
- 外部リンクは新しいタブで開く場合でも、出典 URL を画面に表示する
- 未知の HTML を `innerHTML` に直接挿入しない。表示値はエスケープする
- 生成 AI の出力を出典や事実として採用しない。台帳に人または検証スクリプトの確認を残す

## 9. やらないこと

Phase 1〜3 では次を作らない。

- 避難の可否、医療の要否、経路の安全を個人へ断定する機能
- 個人の健康・介護・適性・移動履歴によるマッチング
- 実データがない項目の推定値による穴埋め
- 住民投稿を自動的に正しい施設情報として公開する機能
- ルート API、外部地図タイル、リアルタイム警報を必須とする構成
- 2100年までの数値を公式予測値として表示すること
- 認証、通知、決済、管理画面、ネイティブアプリ

## 10. 受け入れ検査

### 10.1 データ検査

```bash
python3 scripts/verify.py
```

最低限、次を検査する。

- JSON が読み込める
- `schema_version` が存在する
- 地区 ID が重複しない
- 数値の単位・対象年・データ状態がある
- `verified` の値に出典と取得日がある
- `missing` と `0` が区別されている
- `not_computable` のスコアを順位に使っていない
- 生成された HTML が出典・限界・注意書きを含む

### 10.2 画面検査

- ブラウザで `prototype/index.html` を開く
- コンソールエラーがない
- 画面幅 390px と 1440px で主要操作ができる
- キーボードだけでシナリオ、地区、根拠を操作できる
- `0`、`未確認`、`比較不可` が目視で区別できる
- 60秒デモの手順を再現できる

### 10.3 変更の検査

主張・計算式・データソースを変更したら、次の3点を同じ変更で更新する。

1. `claims.json` または出典マニフェスト
2. `verify.py` の検査または固定点
3. `evidence/run-log.md`

## 11. 未確定事項

| 論点 | 初期判断 | 決定者・期限 |
| :-- | :-- | :-- |
| 最初の地区 | 既存データが揃う地区を fixture にする | オーナー、Phase 1 開始時 |
| 暑熱データの定義 | クーリングシェルター、給水、日陰等を別カテゴリにする | データ担当、Phase 2 |
| スコアの重み | Phase 1 は順位を出さず、または demo priority と明記 | オーナー＋データ担当 |
| 地図の実装方式 | ローカル SVG/GeoJSON を第一候補 | UI担当、Phase 4 着手時 |
| 現地検証の協力先 | 自治体・地域団体・施設管理者 | オーナー、Phase 3 |

未確定事項を解決するために、未検証データを仮定で埋めてはいけない。決定できない場合は、画面に「未確認」として残し、実装を前へ進める。
