# SILVERPUNK PROOF MAP — 自律実装エージェント規約

このファイルは、エージェントが人の逐次指示なしに、実装・検証・引き渡しまで進めるための作業契約である。対象アプリは `apps/silverpunk-proof-map/`。設計上の原本は同じディレクトリの設計仕様書と実装計画書である。

## 1. 着手前に読むもの

必ず次の順で読む。

1. この `AGENT.md`
2. [`20260823-silverpunk-proof-map-design-spec.md`](./20260823-silverpunk-proof-map-design-spec.md)
3. [`20260823-silverpunk-proof-map-implementation-plan.md`](./20260823-silverpunk-proof-map-implementation-plan.md)
4. 自分が担当する `tasks/Txx-*.md`
5. 既存の `apps/tokyo-aging-stress-test/AGENTS.md`（データ検証・公開リポジトリの基本姿勢を参考にする）

既存アプリをコピーして仕様を省略しない。再利用できるデータ処理だけを出典つきで移植する。

## 2. 最初の判断

このプロジェクトの最初の成功は、立派な地図ではなく、**根拠と限界を表示する静的デモが動くこと**である。

したがって、次の順で進める。

1. `apps/silverpunk-proof-map/` の最小構成を作る
2. `data/demo-fixture.json` と `scripts/verify.py` を作る
3. `prototype/index.html` を開く
4. 地区一覧・詳細・根拠・30日カードを追加する
5. 実データの取得・正規化・地図を後から足す

取得できないデータを理由に Phase 1 を止めてはいけない。未検証・欠損として正しく表示して前へ進む。

## 3. エージェント・ハーネス

### 3.1 状態機械

```text
READY → DOING → VERIFYING → DONE
              └────────────→ BLOCKED
```

- `READY`: 依存タスクが完了し、着手可能
- `DOING`: 自分が担当として確保した状態
- `VERIFYING`: 実装は終わり、検査と画面確認をしている状態
- `DONE`: 受け入れ条件と証跡が揃った状態
- `BLOCKED`: 外部状態または決定待ち。推測で埋めず、代替案を試した後に記録する

### 3.2 タスクの確保

1. `tasks/` から依存が満たされた最小 ID の `status: ready` を選ぶ
2. ファイル先頭を `status: doing` に変更する
3. 変更を開始する前に、担当ファイルと依存を確認する
4. 他エージェントの `doing` タスクのファイルを編集しない

共有チェックアウトで競合が予想される場合は、勝手に上書きしない。変更対象を絞るか、`BLOCKED` にして引き渡す。

### 3.3 1タスクの自律ループ

```text
read → claim → implement smallest slice → run verify → inspect browser
     → update evidence → mark done / blocked → hand off
```

各ループで必ず次を行う。

- 変更前に `git status --short` を確認する
- 担当外の既存変更を消さない
- 実装後に最低1つの自動検査を実行する
- UI タスクはブラウザで実際に開く。開けない場合は理由を記録する
- `evidence/run-log.md` にコマンドと観測結果を残す
- タスクファイル末尾に変更概要と残課題を追記する

## 4. ファイルの責務

| ファイル | 責務 | 直接編集する人 |
| :-- | :-- | :-- |
| `data/demo-fixture.json` | Phase 1 の再現可能な入力 | Data担当 |
| `data/raw/` | 公開元から取得した原本 | Data担当 |
| `data/normalized/` | 型・列・コードを揃えた中間データ | Data担当 |
| `data/proof_map.json` | 画面入力の生成物 | Build担当 |
| `scripts/fetch_sources.py` | 取得だけ。画面ロジックを書かない | Data担当 |
| `scripts/normalize_data.py` | 定義・単位・自治体コードの整合 | Data担当 |
| `scripts/build_dataset.py` | 決定的な JSON 生成 | Data担当 |
| `scripts/verify.py` | データ・主張・生成物の検査 | QA担当 |
| `prototype/` | 見せる画面 | UI担当 |
| `evidence/sources.json` | URL、取得日、検証状態 | Data担当 |
| `evidence/claims.json` | UI の主張と根拠の対応 | QA担当 |
| `evidence/run-log.md` | 実行証跡・未解決事項 | 全担当（追記のみ） |
| `tasks/Txx-*.md` | 進捗と引き渡し | 担当エージェント |

画面コードに数値・出典 URL・計算式をハードコードしない。必要な値は JSON または台帳から渡す。

## 5. コマンド契約

アプリディレクトリで実行する。

```bash
python3 scripts/verify.py
python3 scripts/build_dataset.py       # 存在する場合
python3 scripts/build_prototype.py    # 存在する場合
python3 -m http.server 8000
```

Phase 1 では生成スクリプトが未実装でもよいが、その状態を README と run log に書くこと。検査に合格しないまま `done` にしてはいけない。

## 6. データと主張の安全規約

- 数字を作らない。出せない値は `null` と状態ラベルで表示する
- `0`、`missing`、`not_verified`、`not_comparable`、`not_applicable` を区別する
- URL を見ただけでは `verified` にしない。ファイルを開き、粒度・定義・取得日を確認する
- 取得元の更新で固定点が変わったら、数字を検査に合わせて改ざんせず、差分と理由を記録する
- 2050年や2045年で切れる推計を2100年まで外挿しない
- 2100年のシナリオ値は、公式予測値ではなく「シナリオ」または「仮定」と明示する
- 個人の健康、介護、適性、位置履歴、連絡先を保存しない
- 「危険」「安全」「避難できる」と断定しない。比較用の優先候補と、現地確認の必要性を示す
- 住民・高齢者を脆弱性だけで表現しない。利用者・担い手・地域資源として表現する
- 生成 AI の文章を一次情報扱いしない。出典 URL と検証状態を人またはスクリプトで確認する

## 7. データ取得が失敗したとき

次の順で復旧を試す。

1. 既存の検証済み raw/snapshot がないか探す
2. 公式カタログや機械向け URL があるか確認する
3. User-Agent、文字コード、ファイル形式、先頭行、サイズを確認する
4. 形式変更なら取得を止め、差分を `OPEN-ISSUES.md` または `run-log.md` に書く
5. Phase 1 fixture に戻り、基準日を明示してデモを継続する

403、空ファイル、HTML ポインタ、CAPTCHA を成功と扱わない。取得できない値を平均・ゼロ・手入力で補完しない。

## 8. スコアの扱い

スコアは「実証候補の比較」にのみ使う。次の場合は計算しない。

- 必須入力のどれかが `verified` でない
- 地区の粒度・対象年・定義が一致しない
- 正規化範囲または重みが台帳にない
- 欠損を補った値を使うことになる

計算できない場合は、一覧で `算出不可`、詳細で不足入力と次に取得するデータを表示する。

## 9. ブラウザ確認

UI タスクでは、少なくとも次を目視する。

- シナリオを選ぶと表示内容が変わる
- 地区カードを押すと詳細が開く
- 根拠と欠損が見える
- `0` と `未確認` が違って見える
- 390px 幅でも主要操作ができる
- キーボード Tab で操作対象が追える
- コンソールエラーがない

ブラウザ自動化が使えない場合は、ローカルサーバーを起動した日時、URL、目視した項目を run log に残す。スクリーンショットを保存できる場合は `evidence/` に置く。

## 10. BLOCKED の条件

次のすべてを満たすときだけ `blocked` にする。

1. 仕様どおりの安全な代替実装を試した
2. 外部状態（公開元停止、未決定の地区、必要な境界データ等）が必要
3. 推測・捏造なしに残作業を進められない
4. run log に、試したこと、エラー、必要な判断、代替案を書いた

「難しい」「時間がかかる」だけでは blocked にしない。地図をカードへ、リアルタイム取得を snapshot へ、スコアを指標一覧へ縮小して進める。

## 11. DONE の条件

タスクを done にする前に、次をタスクファイルへ記録する。

```text
実装: 変更したファイルと要点
検査: 実行したコマンド
観測: 画面・件数・固定点などで確認した結果
残課題: 次のエージェントが知るべきこと
```

Phase 1 全体は次で完了とする。

```bash
python3 scripts/verify.py
python3 -m http.server 8000
```

さらに、3地区以上、地区詳細、根拠、欠損、30日カードを実際に確認し、`evidence/run-log.md` に記録する。

## 12. 次のエージェントへの引き渡し

引き渡しメッセージは次の形式にする。

```text
[Txx done]
変更: <ファイル>
検査: <コマンド>
観測: <具体的な結果>
注意: <未検証データ、表示上の制約、次の作業>
```

エージェントは、未解決事項を隠して「完成」と言わない。次の担当が、run log と task file だけを読めば続行できる状態を作る。
