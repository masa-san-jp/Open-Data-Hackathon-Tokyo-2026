# 東京10分生活圏・地域役割プラットフォーム 設計仕様書

作成日: 2026-08-23  
版: v0.1  
対象リポジトリ: `masa-san-jp/Open-Data-Hackathon-Tokyo-2026`  
新規アプリ配置案: `apps/tokyo-proximity-role-platform/`

## 0. 決定事項

本プロダクトは、次の2系統を明確に分けて段階実装する。

1. **地図系統**
   - 単身・高齢世帯が、食・一次医療・薬局・福祉・近距離交通等へ実効徒歩5/10/15分でアクセスできるかを可視化する。
   - 歩行速度、道路経路、高低差を条件として再計算する。
   - 既に充足している場所より、改善対象地域を抽出する。
   - 施設追加、Human Bridge、短距離モビリティを仮置きし、改善対象世帯数を比較する。

2. **地域役割系統**
   - 地図で発見した地域課題を、雇用・シルバー人材・障害者雇用・福祉的就労・地域参加等で扱える「地域役割カード」へ分解する。
   - AIは作業分解と制度候補の提示までを行う。
   - 法的区分、本人との最終マッチング、契約判断は人間のコーディネーターと既存支援機関が行う。
   - 通常の求人サイトは作らない。

既存の `apps/tokyo-aging-stress-test/` は別プロダクトとして維持する。  
同アプリの `AGENTS.md`、タスク分割、静的プロトタイプ生成方式は再利用するが、データと主張は混在させない。

## 1. プロダクト定義

### 1.1 名称

- 開発名: `Tokyo Proximity & Regional Role Platform`
- 表示名候補: **東京10分生活圏・地域役割マップ**
- app slug: `tokyo-proximity-role-platform`

### 1.2 解く問い

地図系統:

> 単身・高齢世帯が多い地域のうち、生活に必要な近隣機能へ実効徒歩5/10/15分で届かない場所はどこか。  
> その不足は、施設配置、人的支援、短距離モビリティのどれで改善できるか。

地域役割系統:

> 改善まで人が担える地域課題を、誰が実行可能な作業へ分解し、既存の就労・福祉・地域参加制度へどう接続するか。

### 1.3 主な利用者

| 利用者 | 主な用途 |
|---|---|
| 東京都・区市町村 | 改善対象地区の選定、施策比較、実証地区の設計 |
| 地域就労・福祉コーディネーター | 地域課題の作業分解、制度ルーティング |
| 交通・小売・医療・福祉事業者 | 拠点・サービス配置の検討 |
| 就労支援機関 | 地域役割カードの受入れ、本人とのマッチング |
| 住民 | 地域の現状と改善案の確認。住民投稿は後続フェーズ |

### 1.4 対象外

MVPでは次を行わない。

- AIによる自動採用・自動契約
- 診断名、生バイタル、医療記録による選別
- GPS常時計測
- 住民要望・感情の大量収集
- 労働者性・契約形態の自動確定
- 未確認データを推定で補って「実測値」と表示すること
- 東京都全域を最初から完全網羅したと主張すること

## 2. フェーズ構成

| フェーズ | 系統 | 成果物 | 次フェーズへのゲート |
|---|---|---|---|
| **D0 即時デモ** | 共通 | オフラインで開く単一HTML。デモデータを明示 | 5/10/15分、速度、勾配で色が変わる |
| **M1 地図MVP** | 地図 | 1地域・確認済みデータによる実効徒歩圏 | 出典・粒度・カバー率を画面表示 |
| **M2 対象拡張** | 地図 | 複数区市町村または東京都全域 | カバー率レポートをオーナー承認 |
| **M3 改善シミュレーション** | 地図 | 施設・Human Bridge・モビリティ介入比較 | 改善世帯数と前提を再現可能に出力 |
| **R0 地域役割設計** | 役割 | 未充足セルから地域役割カードを生成 | 人間が編集・承認できる |
| **R1 制度ルーティング** | 役割 | 既存支援ルートの候補提示・案件管理 | 自動確定せず担当者が承認 |
| **R2 人間承認型マッチング** | 役割 | 本人候補と役割の候補照合 | プライバシー・法務レビュー完了 |
| **P 実証運用** | 統合 | 実地域での案件・成果・改善ログ | 行政・支援機関との運用合意 |

D0とM1をハッカソンの最短デモ対象とする。  
R0は地図から「地域課題を人の役割へ変換できる」ことを示すデモまでに限定し、R1以降は別フェーズとする。

## 3. 地図系統の仕様

### 3.1 分析単位

- 初期値: **250mメッシュ**
- データ精度または処理量により500mへ変更可能
- 画面には実際の分析単位を常時表示する
- 町丁目データをメッシュへ按分した場合は、按分方法をメタデータへ記録する
- 直線半径ではなく、可能な範囲で道路ネットワーク到達圏を用いる

### 3.2 近隣生活機能

MVPの対象候補を次とする。データ監査で「利用可能」と判定されたものだけを有効化する。

| code | 機能 | 例 | 現時点の確認状態 |
|---|---|---|---|
| `food` | 食料取得 | スーパー、小型食品店等 | **東京都全域を覆うODは未確認** |
| `pharmacy` | 服薬 | 調剤薬局 | カタログ内の存在確認済み。全都カバー未監査 |
| `clinic` | 一次医療 | 診療所 | カタログ内の存在確認済み。全都カバー未監査 |
| `welfare` | 福祉 | 介護サービス事業所等 | カタログ内の存在確認済み。全都カバー未監査 |
| `toilet_rest` | 排泄・休息 | 公衆トイレ、公園等 | カタログ内の存在確認済み。網羅性未監査 |
| `mobility_node` | 圏外接続 | バス停、地域交通乗降点 | GTFS・停留所データの存在確認済み。全都カバー未監査 |
| `activity` | 活動・地域接点 | 公共・交流施設等 | データ選定未完了 |

「データセットが存在する」と「東京都全域の分析にそのまま使える」は区別する。  
出典ごとに `coverage_status` を保持し、未確認・部分カバー・全域カバーを画面とデータへ残す。

### 3.3 歩行条件

ユーザーは次を変更できる。

- 時間閾値: `5 / 10 / 15` 分
- 基準歩行速度: プロファイル選択または数値入力
- 高低差補正: ON/OFF
- 階段回避: 将来対応
- 雨天・暑熱: 将来対応

#### 経路コスト

各道路リンクの所要時間は次の構造で計算する。

```text
edge_time =
  horizontal_distance / base_walking_speed
  × slope_factor(profile, grade, direction)
  + crossing_delay
  + stairs_penalty
```

D0では `crossing_delay=0`、`stairs_penalty=0` を許容する。  
D0の勾配係数は**デモ仮定**として画面に明示し、実測値とは表示しない。  
M1以降は採用モデル・パラメータ・根拠を `data/methodology/` に固定する。

#### 必須性質

- 歩行速度を下げても到達セルが増えない
- 閾値を5→10→15分と広げると到達セルが減らない
- 同一経路の上り補正を有効化して所要時間が短くならない
- データ欠損を「未充足」と扱わない

### 3.4 メッシュの状態

各メッシュについて以下を保存する。

```json
{
  "cell_id": "53394612-001",
  "geometry": {},
  "analysis_resolution_m": 250,
  "elderly_population": 0,
  "elderly_single_households": 0,
  "data_quality": {
    "population": "verified",
    "food": "unassessed",
    "clinic": "partial"
  },
  "access_minutes": {
    "pharmacy": 7.2,
    "clinic": 9.1,
    "welfare": 13.4,
    "mobility_node": 4.8
  },
  "unmet_services": ["welfare"],
  "classification": "partial_deficit"
}
```

### 3.5 色の意味

時間・速度・勾配条件を変更するたびに再判定する。

| 色 | 状態 |
|---|---|
| 青 | 有効化された必須機能がすべて閾値内 |
| 黄 | 1機能が閾値外 |
| 橙 | 2機能以上が閾値外 |
| 赤 | 複数機能が閾値外、かつ対象世帯数が優先基準以上 |
| 灰ハッチ | データ不足・未評価 |
| 薄灰 | 対象人口が基準未満。評価値自体は保持 |

赤は「不便」のみで決めず、**未充足数 × 高齢単身世帯等の需要量**で決める。  
優先基準は設定ファイル化し、UIに値を表示する。

### 3.6 UI

```text
┌─────────────────────────────────────────────────────┐
│ 対象: 高齢単身世帯 | 5/10/15分 | 歩行速度 | 勾配 ON/OFF │
├──────────────┬──────────────────────┬───────────────┤
│ レイヤー      │ 地図                  │ 選択地域詳細    │
│ 人口・世帯    │ メッシュ塗り分け      │ 対象世帯数      │
│ 薬局          │ 施設点は任意表示      │ 各機能の時間    │
│ 診療所        │ 改善対象を強調        │ 不足理由        │
│ 福祉          │                       │ データ品質      │
│ 交通          │                       │ 出典            │
├──────────────┴──────────────────────┴───────────────┤
│ 改善モード: 生活拠点 / Human Bridge / モビリティノード │
└─────────────────────────────────────────────────────┘
```

初期表示では施設点を大量表示しない。  
メッシュをクリックしたときだけ、そのセルに影響する施設・経路・データ品質を表示する。

### 3.7 改善シミュレーション

介入タイプ:

| type | 内容 | 初期パラメータ |
|---|---|---|
| `local_service_point` | 食料・薬受取等の小規模拠点 | 位置、提供機能 |
| `human_bridge` | 配送・同行・送迎等の暫定人的支援 | 対象範囲、稼働時間、容量 |
| `mobility_stop` | 短距離モビリティ乗降点 | 位置、待ち時間、速度、接続施設 |
| `mobility_route` | 巡回またはオンデマンド運行 | 停留点、速度、運行間隔 |

出力:

- 閾値内へ入る追加世帯数
- 高齢単身世帯の改善数
- 改善される機能
- 変化前後のメッシュ色
- 使用した仮定
- データ品質

D0では容量・費用の最適化は行わない。  
M3で複数介入の比較と、概算コスト入力欄を追加する。

## 4. 地域役割系統の仕様

### 4.1 定義

地域役割系統は「求人掲示板」ではない。

```text
地図上の未充足
  ↓
地域課題の型を特定
  ↓
作業単位へ分解
  ↓
地域役割カード
  ↓
既存制度・支援機関の候補提示
  ↓
人間のコーディネーターが承認
  ↓
各機関が本人とマッチング
```

### 4.2 地域課題から役割への変換例

| 地域課題 | 作業例 |
|---|---|
| 食料アクセス不足 | 注文受付、商品ピック、短距離配送、受渡し、買物同行 |
| モビリティ導入前 | 予約受付、短距離送迎、乗降支援、ルート案内 |
| 薬局アクセス不足 | 薬受取、配送、利用案内。医療行為は対象外 |
| デジタル手続き困難 | 端末操作支援、予約補助。代理権限が必要な手続きは対象外 |
| 地域交流不足 | 案内、会話、イベント運営、技能・文化伝承 |

役割テンプレートは承認済みカタログから選び、AIが自由生成したまま公開しない。

### 4.3 地域役割カード

```json
{
  "role_id": "ROLE-0001",
  "source_cell_id": "53394612-001",
  "problem_type": "food_access",
  "title": "電話・端末による注文受付",
  "location": {},
  "schedule": {
    "min_minutes": 60,
    "frequency": "weekly"
  },
  "task_units": [
    "注文内容を定型画面へ入力",
    "受渡し時間を案内"
  ],
  "functional_requirements": {
    "main_posture": "seated",
    "lifting_kg_max": 0,
    "standing_minutes_max": 10,
    "customer_contact": true
  },
  "supervision": "required_initially",
  "compensation_required": true,
  "route_candidates": [
    "senior_employment",
    "disability_employment",
    "welfare_work"
  ],
  "legal_status": "human_review_required",
  "status": "draft"
}
```

診断名ではなく、作業に必要な**機能条件**を記述する。

### 4.4 誰が何をするか

| 主体 | 責任 |
|---|---|
| 東京都 | 共通基盤、役割カード標準、コーディネーター育成、評価指標 |
| 区市町村 | 改善対象地区と地域課題の選択 |
| 地域役割設計担当 | 現地確認、作業分解、役割カード編集 |
| 既存就労・福祉支援機関 | 制度適合確認、本人との相談、最終マッチング |
| 受入事業者・地域団体 | 作業環境、指揮命令、報酬、事故対応の確定 |
| AI | 下書き、タスク分解、候補ルート提示、説明文生成 |
| AIがしないこと | 契約区分確定、採否決定、医療判断、本人意思の代行 |

### 4.5 制度ルーティング

初期の候補コード:

- `senior_employment`
- `silver_human_resources`
- `disability_employment`
- `welfare_work`
- `community_participation`
- `commercial_service_provider`

ルールエンジンは候補を提示するだけとし、次を自動確定しない。

- 雇用か請負か
- 最低賃金法の適用
- 障害福祉サービスとしての適合
- 本人の支援計画への組込み
- 有償ボランティアとして扱えるか

### 4.6 マッチングの段階

| 段階 | 個人情報 | 機能 |
|---|---|---|
| R0 | なし | 地域役割カード生成・編集 |
| R1 | 担当機関情報のみ | 案件を支援機関へルーティング |
| R2 | 本人同意済みの最小プロフィール | 候補照合、理由表示、人間承認 |
| P | 運用に必要な情報 | 契約・支援は既存機関のシステムで管理 |

R2以前にGPS、生バイタル、診断名を取得しない。

## 5. データ管理

### 5.1 データレジストリ

すべてのデータを `data/catalog.yaml` に登録する。

必須項目:

```yaml
id: tokyo_clinics_example
title: 診療所情報
provider: 自治体名
source_url: https://...
license: ...
retrieved_at: 2026-08-23
geography: point
granularity: facility
coverage:
  area: ...
  status: partial
schema_status: verified
production_ready: false
notes: 全都カバー未監査
```

### 5.2 保存階層

```text
data/
├── catalog.yaml
├── demo/             # デモ用。画面に「DEMO DATA」を表示
├── raw/              # 原本。変更しない
├── normalized/       # 共通スキーマ
├── processed/        # メッシュ・到達時間・分類
├── methodology/      # 歩行速度・勾配補正等
└── reports/          # カバー率・欠損・検証結果
```

## 6. システム構成

### 6.1 即時デモ

```text
scripts/build_demo.py
  ├─ data/demo/cells.json
  ├─ data/demo/infrastructure.json
  ├─ data/demo/roles.json
  └─ templates/demo.html
        ↓
```

条件:

- ダブルクリックまたは `python3 -m http.server` で開く
- 外部API・CDN不要
- データはHTMLへ埋め込む
- `DEMO DATA / NOT FOR POLICY DECISION` を常時表示
- 地図は簡略GeoJSONまたはSVGグリッドでよい
- 色変化、セル詳細、介入前後、役割カード下書きを実演する

### 6.2 M1以降

```text
web/          React + TypeScript + MapLibre GL JS
api/          FastAPI
pipeline/     Python geospatial ETL
db/           PostgreSQL + PostGIS（M2/R1から）
prototype/    オフラインデモ
scripts/      build / verify / screenshot
tasks/        エージェント用タスク
```

D0/M1ではPostGISを必須にしない。  
静的JSONで完了できる範囲を先に出す。

## 7. プライバシー・安全

- 地図MVPは個人データを扱わない
- 住民・候補者の自宅位置を公開しない
- メッシュ内人数が少ない場合は秘匿または集約する
- 候補者プロフィールはR2まで実装しない
- 機能制約は本人入力・支援者確認を基本とし、診断名を役割提供者へ渡さない
- AIの推薦理由、使用項目、除外理由を保存する
- マッチングは常に `proposed → human_review → approved/rejected`
- `approved` をAIが直接作成できない

## 8. 受入条件

### D0

- `prototype/index.html` がオフラインで開く
- 5/10/15分切替で色が変化する
- 歩行速度変更で到達圏が変化する
- 勾配ONで対象セルの時間が変化する
- 未評価セルが赤ではなく灰ハッチになる
- セルを選ぶと不足機能・世帯数・前提が表示される
- モビリティノード仮置きで改善世帯数が変化する
- 地域役割カードを1件生成できる
- 画面にデモデータ表示がある

### M1

- 1地域について全入力データの出典、取得日、ライセンス、範囲を提示
- 道路・標高・施設・人口の結合を再現できる
- データ欠損レポートを出力
- 同じ入力から同じ結果を再生成できる

### R0

- 役割カードは地図上の課題に紐づく
- 作業、時間、身体負荷、監督、報酬要否を編集できる
- 制度候補は複数提示可能
- 人間承認なしに公開・マッチングされない
