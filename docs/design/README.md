# 設計仕様書・実装計画 (docs/design)

作品全体の設計仕様書と実装計画の置き場。

## 他ディレクトリとの役割分担

| 場所 | 置くもの |
| :-- | :-- |
| `docs/planning/` | 何を作るかの比較・評価の**過程** |
| `docs/proposal/` | 企画書へ転記する**確定結論** |
| **`docs/design/`（ここ）** | **どう作るかの設計仕様・実装計画**（画面・データモデル・API・処理フロー・工程表） |
| `apps/<app>/SPEC.md`・`apps/<app>/tasks/` | そのアプリ固有の仕様・タスク分解（コードの隣に置く） |

複数アプリにまたがる設計、実装前のアーキテクチャ検討、当日の工程表はここに置く。
1つのアプリに閉じた詳細仕様は `apps/<app>/` 側が正。両方に書く場合はアプリ側を正とし、ここからリンクする。

## プロジェクト

- [`living-zone-navi/`](./living-zone-navi/) — 暑さと災害に強い生活圏ナビ。江東区を既定対象に、涼み処・避難所・医療・介護への到達性とデータ欠損を、すぐ動くHTMLデモとして実装する。
- [`silverpunk-proof-map/`](./silverpunk-proof-map/) — 高齢者・要配慮者のための暑熱・災害対応生活圏ナビ。設計仕様、実装計画、自律実装用 `AGENT.md`、タスク分解を含む。
- [`20260823-tokyo-proximity-role-platform/`](./20260823-tokyo-proximity-role-platform/) — 近接×役割のプラットフォーム設計。設計仕様・実装計画・エージェントハーネスを含む。

## 命名

`YYYYMMDD-<kebab-case>.md`（リポジトリ共通の規約）。
種別が分かる接尾辞を推奨: `-design-spec.md`（設計仕様）／`-implementation-plan.md`（実装計画）。

## 書き方の約束

- 仕様には「やらないこと（スコープ外）」を必ず書く
- 実装計画には時間配分と、遅れたときのフォールバック条件を書く
- 未確定事項は「未確定」と明示し、決定者を書く
