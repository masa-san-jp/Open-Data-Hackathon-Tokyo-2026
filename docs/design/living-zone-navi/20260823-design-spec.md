# 設計仕様書 — 暑さと災害に強い生活圏ナビ

作成日: 2026-08-23 ／ 実装先: `apps/living-zone-navi/` ／ 状態: 実装可

## 1. 主張（画面で最初に伝わるべき一文）

> あなたの町の高齢者は、歩いて涼める場所・避難できる場所に届くか。
> 届かない町がどこかと、**そもそもデータが無くて分からない町がどこか**を、東京都オープンデータだけで見せる。

「全部つながった綺麗な地図」ではなく、**届く／届かない／分からない の3値**を主役にする。
（補助金実測で確立した「追えないものを見せる」型の地理版）

## 2. 対象の固定（C1: 実証単位を1つに絞る）

| 軸 | 既定値 | 根拠 |
| :-- | :-- | :-- |
| 区 | **江東区** | カタログ実測でクーリングシェルター・医療機関ODが区単位に実在する数少ない区 |
| 利用者像 | 75歳以上（後期高齢者）を第一、65歳以上を切替表示 | 2100年の東京は1/3が75歳以上 |
| 徒歩閾値 | 300m（気軽）／800m（徒歩10分・限界） | 高齢者歩行速度 ~4km/h の10分圏。UAD「300mごとの休憩インフラ」と整合 |
| 対象拠点 | ①避難所 ②クーリングシェルター等の涼み処 ③医療機関 ④介護・福祉施設 | 都民の声 c01/c05/c06/c09 に対応 |

区は `config.json` の `ward` で差し替え可能に作る（ハードコードしない）。

## 3. データ（すべてURLはカタログCSVから解決し sources.json に記録）

| # | データ | 探し方（カタログのタイトル検索語） | 用途 | 無い場合 |
| :-- | :-- | :-- | :-- | :-- |
| D1 | 避難所・避難場所 | 「避難所」「避難場所」＋区名 | 拠点① | 都全域データで代替 |
| D2 | クーリングシェルター/涼み処 | 「クーリングシェルター」「暑さ」 | 拠点② | **「未公開」として欠損表示（消さない）** |
| D3 | 医療機関 | 「医療機関」「病院」＋区名 | 拠点③ | 都保健医療局の全域一覧 |
| D4 | 介護・福祉施設 | 「介護」「福祉施設」 | 拠点④ | 都福祉局の全域一覧 |
| D5 | 町丁別・年齢別人口 | 「住民基本台帳」「町丁」＋区名 | 需要側（65+/75+人口） | 区の年齢別人口（区一括）に落とす |
| D6 | 町丁目の位置（代表点） | 国土交通省 位置参照情報（大字・町丁目レベル、東京都13） https://nlftp.mlit.go.jp/isj/ | D5と施設の距離計算 | Phase 0 は距離計算なしで成立（§6） |

原則: **座標列が実データに無い施設は距離計算から除外し「位置不明 n件」として集計・表示**する。

## 4. データモデル（processed/dataset.json）

```json
{
  "meta": { "ward": "江東区", "built_at": "…", "sources": [ {"id":"D1","url":"…","fetched_at":"…","sha256":"…"} ] },
  "facilities": [
    { "id": "D1-0001", "kind": "shelter|cool|medical|care",
      "name": "…", "lat": 35.6, "lon": 139.8, "source": {"file":"…","row": 12} }
  ],
  "areas": [
    { "code": "131080010", "name": "○○一丁目", "lat": 35.6, "lon": 139.8,
      "pop_total": 3200, "pop_65plus": 900, "pop_75plus": 480,
      "nearest_m": { "shelter": 240, "cool": null, "medical": 610, "care": 380 },
      "reach": { "shelter": "near|far|out", "cool": "unknown", "medical": "…", "care": "…" } }
  ],
  "gaps": [
    { "kind": "cool", "reason": "not_published", "note": "クーリングシェルターの区別ODが未公開" },
    { "kind": "barrier_free", "reason": "not_collected", "note": "段差・屋根・ベンチ間隔の線データは都ODに存在しない（実測13件）" }
  ]
}
```

- `reach` の判定: `near` ≤300m ／ `far` ≤800m ／ `out` >800m ／ `unknown` = 対象データ欠損または位置不明
- `gaps.reason` は補助金M1と同じ欠損コード語彙（`not_published` / `not_collected` / `not_applicable` / `unknown` / `source_missing` / `extraction_failed` / `under_review`）を再利用。**語彙を新造しない**

## 5. 画面（prototype/index.html・1枚・file://で動く・外部依存ゼロ）

上から順に:

1. **ヘッダ数字4つ**: 対象区／65+・75+人口／「800m以内に涼み処が無い高齢者 n人」／「データ欠損で判定不能 n町丁」
2. **SVG地図**: 町丁代表点を円で描画（半径=75+人口、色=reach: 緑near/黄far/赤out/**灰unknown**）。施設は種別マーカー。投影は経緯度の等座標スケーリング（区スケールで十分）。ホバーで町丁名と距離
3. **ワースト表**: 「届かない高齢者数」上位10町丁（人口×outで降順）
4. **欠損パネル**: `gaps` を理由コード付きで列挙。「これは本作品の不具合ではなく、公開データの現状である」と一文
5. **注記（必ず表示）**: 直線距離であること／位置不明施設の件数／出典URL・取得日一覧
6. **（Phase 2）2100トグル**: 75+人口に係数を掛けるシナリオボタン（§7）

実装: 素のHTML+CSS+JS（フレームワーク・CDN禁止）。データは `build_prototype.py` がJSONをHTMLに**埋め込んで**生成（fetchしない＝file://で確実に動く）。

## 6. 処理フロー（全部決定論・stdlibのみ）

```
fetch_sources.py   カタログCSVからURL解決 → DL → サイズ/先頭行検査 → data/raw/ + sources.json
build_dataset.py   cp932/utf-8判定 → 施設正規化(kind付与・座標検査) → 町丁人口結合
                   → haversine距離 → reach判定 → gaps生成 → data/processed/dataset.json
build_prototype.py dataset.json を埋め込んだ prototype/index.html を生成
verify.py          固定点検査（§8）
```

## 7. Phase 2: 2100ストレステスト（接続仕様）

`apps/tokyo-aging-stress-test/` の出力から対象区の高齢者係数を読む。読めない場合の既定値:
75+人口 ×1.5（2070年相当）／×2.0（2100年相当・転入半減）。**係数は config.json に置き、出所を注記に表示**。
予測ではなくストレステストである旨を画面に明記（planning の原則そのまま）。

## 8. verify.py の固定点（最低限）

- sources.json の全URLに取得日とsha256がある
- facilities: 件数>0、緯度が北緯35〜36度・東経139〜140度の範囲外なら fail
- areas: pop_65plus ≤ pop_total、reach値は5値のみ
- **gaps が空なら fail**（欠損ゼロはこのデータ環境ではあり得ない＝取り漏らしの兆候）
- index.html が存在し、「直線距離」「取得日」の文字列を含む

## 9. やらないこと（スコープ外）

- 経路検索・道路ネットワーク・段差考慮のナビ（データが無い。無いことを画面で言う）
- ジオコーディング（住所→座標の補完）
- 個人の健康情報を使うマッチング（HaaS）
- 多区同時表示（Phase 3 の比較表まで。地図は常に1区）
- 予測の断定（2100はストレステスト表示のみ）
