# コンセプトリサーチ (docs/concept-research)

作品のコンセプトを設計し、実装・実測へ進む前に、成立条件・先行事例・設計要件・反証・シナリオを整理する場所。

`docs/research/` が「世の中で何が分かっているか」を集める場所なのに対して、
ここは「この作品を成立させるには何が必要か」「どの前提が崩れうるか」を、
作品固有の問いに沿って調査・設計する場所である。

このディレクトリでいう「検証」は、主にコンセプトの成立条件を確認する探索段階を指す。
実測による因果関係の証明や、本番導入の効果測定を完了したという意味ではない。
試算・シナリオモデル・コードは、前提と限界を明記したうえで置く。

## 何を置くか

| 置く | 置かない |
| :-- | :-- |
| コンセプトの問い、設計上の仮説、成立条件 | 出典のない数字や、検証前の断定 |
| 国内外の先行事例と、作品への適用可能性の比較 | 一般的な業界動向だけの整理（→ `docs/research/`） |
| 住環境・労働・医療・移動などの要件、設計原則、アーキテクチャ | 調査結果と提案を混同した記述 |
| 反証、リスク、制度上・運用上の制約 | 個人名・連絡先・非公開の第三者情報 |
| 再現可能な試算、シナリオモデル、検証案 | 結果を見てから前提や判定基準を変更した記録 |
| 未決事項と、次に確かめるべきこと | 都合のよい根拠だけを残した結論 |

## 現在の資料の位置づけ

- **SILVERPUNK // 2100**：超高齢都市のコンセプト、職住医福インフラ、労働・集客・医療・移動の成立条件
- **ユニバーサルアシストデザイン（UAD）**：人・ものの移動を支える環境・機器・情報の三層設計
- **東京2100**：先行事例、人口動態、転入ゼロなどのシナリオ分析
- **戦略・作戦計画**：調査結果をもとにしたバックキャスト、優先順位、実装フェーズ

## 1件の書き方

```markdown
# <テーマまたはコンセプト上の問い>

- 目的:
- 対象・スコープ:
- 現段階: 探索中 / 設計案 / 再現可能な試算 / PoC準備
- この調査が変える設計判断:

## 問いと前提

何を明らかにしたいか。前提・仮説・反実仮想条件を分けて書く。

## 先行事例・根拠

| 事例・論点 | 分かったこと | 適用できること | 限界 | 出典URL | 取得日 |
| :-- | :-- | :-- | :-- | :-- | :-- |

## 成立条件・設計要件

構想を成立させるために必要な制度、技術、運用、KPIを書く。

## 反証・リスク

成立しない可能性、反対材料、撤退条件を書く。否定的な結果も削除しない。

## シナリオ・試算・検証案

試算やコードを使う場合は、入力データ、計算式、再現手順、判定基準を明記する。
判定の閾値を使う場合は、結果を見る前に定める。

## 未決事項・次の調査

まだ確かめられていないこと、追加で必要なデータ、次の意思決定を書く。

## 参考資料

URL、資料名、取得日、ライセンスを整理する。
```

## 記述と再現のルール

- **事実・解釈・提案を分ける。** 先行事例からの推論は、推論であることを明示する。
- **数字には出典URLと取得日を付ける。** 可能な限り一次資料を優先する。
- **再現可能な計算は、コード・入力データ・実行方法・制約を残す。**
- **反証や未検証事項を残す。** コンセプトを強くするために、不都合な根拠も消さない。
- **公開リポジトリであることを前提にする。** 個人情報、連絡先、非公開情報を置かない。

## 命名

`YYYYMMDD-<kebab-case-の内容>.md`（`docs/research/` と同じ）。
テーマが増えて整理が必要になったら、`<テーマ名>/` のようにサブディレクトリで束ねる。
